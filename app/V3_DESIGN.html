Advanced AI Engineering · Version 3 · High-Level Design

EdgentRAG v3 — the version that survives

The same product, rebuilt so that hundreds of people can use it at once and nothing is lost when a machine goes away. One rule drives every decision here.

What this document is. Version 2 adopts the code half of this design — async endpoints and SQS-backed workers — on version 1's single-machine deployment. Everything below about managed infrastructure (Fargate, RDS, a load balancer) is the step after that, described here so the reason for each piece is on record before it is needed.

Part 0The one rule

Version 1 works and is worth having built. Everything that breaks in it traces back to a single decision, and version 2 is mostly the consequence of reversing that decision:

The rule for version 2

The API never does slow work. It validates a request, writes a row, puts a message on a queue, and returns. Anything that takes longer than a few milliseconds happens somewhere else, in a process whose death costs nothing.

In version 1, background.add_task runs ingestion and answer generation inside the web server, on the same forty-thread pool that serves ordinary requests. That one fact produces most of Part 7 of the version 1 design: forty concurrent operations freeze the whole API, a deploy mid-upload silently destroys the work, and one person's large upload makes another person's page feel broken.

Everything below follows. The queue is not an embellishment; it is the change, and the rest is what a queue makes possible.

What is deliberately out of scope: the three model services. Assume they are excellent — batched, quantised, warm, and fast. This document is about everything around them.

What version 1 already got right

Four things carry over untouched, and it is worth naming them: presigned URLs in both directions, so file bytes never pass through the application; the storage abstraction, so nothing but one file knows what S3 is; settings-driven environments, so a laptop and a cloud are the same program; and service calls that carry data rather than file paths — the lesson version 1 learned painfully when three services moved onto a GPU.

Part 2Every AWS component, and why it is here

Each entry says what the service is, why this design uses it, and what it replaces. If a component cannot be justified by a specific version 1 failure or a specific scaling need, it should not be in the diagram.

Edge — what the internet touches

Amazon CloudFront

CDN

A content delivery network: a few hundred servers around the world that cache your static files and sit in front of your application. It terminates TLS, so certificates are handled in one place, and it serves the React bundle from wherever the user is rather than from one region.

It also absorbs the boring traffic. Every page load fetches the same JavaScript; that should never reach your servers.

Replaces: nginx serving frontend/dist, and a Cloudflare quick tunnel for TLS.

AWS WAF

web application firewall

Rules applied before a request reaches you: rate limits per IP, blocking of known-bad sources, and size caps. Version 1 has no limit on how often anyone may ask a question, and each question costs GPU time — a single script could spend your entire compute budget in an afternoon.

Replaces: nothing. There was no protection at all.

Application Load Balancer

ALB

Spreads requests across however many API tasks are running, and stops sending traffic to any that fail their health check. It is also what makes deploys invisible: new tasks are registered, old ones drained, no request dropped.

It supports long-lived streaming responses, which matters here — the API holds a Server-Sent Events connection open per active chat.

Replaces: nothing — version 1 had a single process with nowhere to balance to.

Route 53 + AWS Certificate Manager

DNS and TLS

A domain you own, and a certificate that renews itself. This is what ends the version 1 situation where the public address changes every time a tunnel restarts and any link you shared stops working.

Replaces: *.trycloudflare.com addresses that live as long as a process does.

Compute — where code runs

Amazon ECS on AWS Fargate

containers, no servers

Fargate runs containers without you owning the machine underneath. You describe a task — this image, this much CPU and memory — and AWS finds somewhere to run it. There is no instance to patch, no disk to fill, and no ssh.

Three separate services run this way, and separating them is the point: the API, the ingest workers, and the chat workers. They fail independently, deploy independently, and scale on different signals.

The API must be written with async def handlers rather than version 1's synchronous ones. It will hold hundreds of idle streaming connections, which asyncio does for almost nothing and a thread pool cannot do at all.

Replaces: one t3.medium running uvicorn under systemd.

Application Auto Scaling

target tracking

Adds and removes tasks to hold a chosen metric steady. The important detail is that the three services scale on different signals:

Amazon ECR

container registry

Where the built images live. Every deploy is an image tagged with a commit, which makes a rollback a matter of pointing at the previous tag rather than reversing a change.

Replaces: rsync of source files onto a running server.

Messaging — the change that matters

Amazon SQS

queues, plus dead-letter queues

A durable list of work. A producer writes a message; a consumer picks it up, and the message stays invisible-but-present until that consumer confirms it is done. If the consumer dies mid-task, the message reappears and someone else takes it.

That single behaviour fixes the worst thing about version 1. There, a deploy during ingestion destroys the work silently and nothing ever retries. Here, killing a worker costs one redelivery.

Three queues, not one. Ingestion is bulk work measured in throughput; chat is interactive work measured in latency. Sharing a queue means somebody's fifty-file upload sits in front of everybody's questions, which is version 1's limit 02 reproduced at a larger scale.

The third is transcribe, and it points the other way: the workers write to it and the speech-to-text service reads from it. That inversion is the subject of Part 5, and it is what removes the last long-held connection in the system.

A dead-letter queue on each. After a handful of failures a message moves aside instead of retrying for ever. Without one, a single corrupt file can occupy a worker permanently.

Delivery is at least once, so handlers must be idempotent — processing the same message twice must be harmless. Version 1 is already most of the way there: chunk ids are deterministic and the vector store upserts rather than inserts.

Replaces: background.add_task, which is a queue with no durability, no retry, and no consumer.

State — what everything shares

Amazon RDS for PostgreSQL

the database

A managed Postgres: backups, patching, failover to a standby in another availability zone, all handled. It replaces a SQLite file, and the reason is not snobbery — SQLite locks the whole file for a write, so ingestion writing status blocks every browser reading it, and the database lives on one instance's disk and dies with it.

Version 1 needs no code change for this. DATABASE_URL already selects the engine; SQLAlchemy does the rest.

Replaces: sqlite:///./local.db on the instance's disk.

pgvector

a Postgres extension

Adds a vector column type and similarity search to Postgres. Chunks, their metadata and their embeddings live in one table, in one system, with one backup and one set of credentials.

This is a deliberate choice over a dedicated vector database. At this scale the simplicity wins: a chunk and its vector are written in the same transaction, so they cannot disagree, and there is no second system to operate. Graduate to OpenSearch Serverless when the index stops fitting comfortably in memory or you want hybrid keyword-and-vector search — and treat that as a planned migration rather than something to pre-build.

Replaces: Chroma on the GPU machine, which died whenever that machine did.

Amazon RDS Proxy

connection pooling

Postgres connections are expensive and limited. Thirty API tasks plus forty workers, each with its own pool, will exhaust a small instance's connection limit long before its CPU. RDS Proxy holds one warm pool and lends connections out, so scaling the fleet does not scale the connection count.

It also shortens failover: the proxy reconnects to the new primary rather than every task discovering the failure on its own.

Replaces: nothing — one process needed no pooling.

Amazon ElastiCache for Redis

cache and message bus

Three jobs, and the second is the interesting one.

The conversation window. Version 1 keeps the last few turns in a Python dictionary, which works only because there is one process. With thirty API tasks, a user's history has to live somewhere all of them can see. The code already anticipates this: memory.py has a Redis implementation behind the same two methods, chosen by a setting.

Pub/sub for streaming. A chat worker generates tokens, but the browser's connection is held by some API task, and the two will not be the same process. The worker publishes tokens to a channel named for the message; whichever API task holds that connection is subscribed and relays them. This is what makes token-by-token streaming work across a fleet.

Ordinary caching. Session status is read constantly and changes rarely.

Replaces: a defaultdict that died with the process.

Amazon S3

files — largely unchanged

Version 1 already uses S3 correctly, and this is the part of it that needs no rethinking. The browser uploads straight to the bucket with a presigned URL, and the speech-to-text service downloads straight from it with another. File bytes never pass through the application, which is why a two-gigabyte video does not require a two-gigabyte server.

One addition: S3 event notifications. When an object lands, S3 puts a message on the ingest queue itself. Version 1 waits for the browser to call /files/register and simply believes it — if the user closes the tab after uploading, the file is never processed. Having storage announce its own arrivals removes that trust.

Add lifecycle rules too: expire raw uploads after some period, keep the extracted text.

Replaces: nothing — it improves on what is already there.

Identity and secrets

Amazon Cognito

user accounts

Sign-up, sign-in, and signed tokens. Version 1 has no notion of a person: a session id is the only identity, nothing verifies it, and anyone holding one can read those documents. With hundreds of users that is not a limitation, it is a data breach.

Every request carries a JWT; every session row gets an owner; every query filters by it.

Replaces: limit 08 — "anyone can read anyone's files".

AWS Secrets Manager and IAM roles

credentials

Database passwords live in Secrets Manager and rotate; everything else uses IAM task roles, which hand short-lived credentials to a running container automatically. Version 1 already does the important half of this — the EC2 instance role means no access key exists to leak. v2 keeps that discipline and extends it per service, so the chat workers cannot write to the bucket and the API cannot read the queue.

Replaces: the instance role, generalised and narrowed.

Network and operations

VPC, subnets, security groups

the network

Public subnets hold only the load balancer. Everything else — API tasks, workers, database, cache — sits in private subnets with no route from the internet. Security groups then allow exactly one hop each: ALB to API, API and workers to database, workers outbound to the model services.

Version 1 gets the spirit of this right on one machine by binding uvicorn to 127.0.0.1. This is the same idea with more machines.

Replaces: a single security group and a loopback bind.

CloudWatch, and OpenTelemetry tracing

seeing what happened

Version 1's last limitation is "when it is slow, you cannot say why", and with one process and a log file that is true. Distributed systems make it worse: a slow answer might be the queue, the database, the retrieval, or the model.

So: structured JSON logs, metrics for queue depth and per-stage duration, alarms on the dead-letter queues and on age-of-oldest-message, and a trace id created at the ALB and carried through the queue message into the worker and out to the model service. The trace is what turns "chat feels slow" into "retrieval is taking 900ms at p99".

Replaces: journalctl on one box.

Calling the model services

The services themselves are out of scope, but how the workers call them is not, and version 1 has none of this. Every call needs a timeout, so a slow service cannot hold a worker for fifteen minutes; retries with exponential backoff and jitter, so a blip does not fail a job and a recovery does not arrive as a thundering herd; and a circuit breaker, so when a service is genuinely down the workers stop hammering it and fail fast instead.

Concurrency also has to be bounded. An autoscaling worker fleet with no limit will happily send five hundred simultaneous requests at a GPU sized for fifty, and turn a fast service into a broken one.

Part 3Getting the files in

The browser still uploads straight to S3. What changes is what happens next: storage announces the arrival, and one message is created per file rather than one task per session.

The API appears once, at the start, and does nothing slow.

One message per file is what turns a fifty-file upload from fifty sequential conversions into fifty parallel ones across the worker fleet. Version 1 processes them in a loop inside a single background task, so the session takes as long as the sum of its files.

A video takes one more hop, and it is a second queue rather than a phone call — see Part 5, which is the part of this design that took the longest to get right.

The session is finished when its last file is. Each worker, on completion, decrements a counter in the same transaction that marks the file done, and whoever takes it to zero marks the session ready. No coordinator is needed.

Chunking must stream. Version 1 splits an entire document into one list of words, which measured at sixteen to twenty-six times the file's size in memory — a hundred-megabyte text file is enough to kill a small machine. A worker reading and emitting chunks incrementally has a flat memory profile regardless of file size.

Part 4Answering a question, in real time

This is where "hundreds of users, in real time" is won or lost. The mechanism is the same queue, plus one addition: the answer is streamed as it is generated rather than delivered when it is finished.

Why polling has to go. Version 1's browser asks "is it done?" every two seconds. With three hundred users that is a hundred and fifty requests a second of pure overhead, none of which carries information most of the time — and the user still waits up to two seconds after the answer exists. Server-Sent Events invert it: the browser opens one connection and the server writes to it when there is something to say.

SSE rather than WebSockets because the traffic is one-directional. The browser has nothing to say mid-answer, and SSE is ordinary HTTP with automatic reconnection built into the browser.

Perceived speed is mostly first-token latency. A four-second answer that starts appearing after 400 milliseconds feels immediate; the same answer delivered whole after four seconds feels slow. This is the single largest user-visible difference between the two versions, and it costs no GPU improvement at all.

The database still receives the finished answer, so a reconnecting browser can recover it. Redis carries the live stream; Postgres remains the record.

Retrieval, unchanged in shape

Embed the question, search, fetch the winning chunks, assemble a prompt. That sequence is identical to version 1 — it was never the problem. The difference is that it now happens in a worker, against pgvector, with the chunk text retrieved in the same query as the vector search rather than in a second round trip to storage.

Part 5Talking to machines you do not own

The three model services run somewhere else — a Colab runtime, a rented GPU box, someone else's account. Two of the workers have to reach them, and it is tempting to treat that as one problem with one answer. It is not.

An earlier draft of this document was wrong about this. It claimed that moving work into a queue meant "nobody is holding a connection waiting". That is true of the browser and true of the API — and false of the worker, which was still making a fifteen-minute synchronous call to a GPU behind a tunnel that closes connections after a hundred seconds. Queueing the front of a system does not fix the back of it.

HopHowWhy
worker → speech to text a queue minutes of work, nobody waiting live, and the GPU should pull when it is ready
worker → embedding, to index a queue bulk work, and a thousand uploads at once must not become a thousand connections
worker → embedding, to query direct call milliseconds, and it sits in the middle of a chat — a queue hop is latency for nothing
worker → language model direct call latency decides how it feels, and you cannot stream through a queue

Why transcription belongs on a queue

It is the textbook workload for one. The job takes minutes, no one is watching it happen, and the failure mode a queue handles — the machine doing the work disappears — is not hypothetical when that machine is a Colab runtime.

The decisive advantage is backpressure. With a direct call, five videos arriving at once become five connections to a service that can transcribe one at a time; four of them sit in a socket burning their timeout budget, and the one that dies is whichever was last in the queue rather than whichever was largest. With a queue, the GPU takes the next message when it has finished the previous one. Nothing waits on a connection, so nothing times out. A backlog is a number you can see and scale on, rather than a failure you discover.

No connection is held open at any point, by anyone.

The message carries its own permissions

The worker puts two presigned URLs into the message: a GET for the video and a PUT for the results. The speech-to-text service reads one, writes the other, and never needs to know your bucket's name, your region, or any credential of yours. The permission is inside the link and it expires.

The results landing in S3 then raises an event that returns the job to the worker fleet, so the GPU does not need to send anything back either. Version 1 already discovered this pattern for uploads and again for downloads; this is the third use of it, and by now it is clearly the shape of the thing.

The same model, two deployments

Embedding appears twice in this system and the two uses have nothing in common except the weights they load. Indexing is bulk work nobody is watching; a query is a few milliseconds with a person waiting at the other end.

Left on one fleet they interfere, and in the direction that hurts. Someone uploading a four-hundred-page document produces hundreds of embedding batches back to back, and every one of them competes with somebody else's question. Chat quietly gets slower whenever anyone uploads anything — version 1's limit 02 again, one layer further down: bulk work starving interactive work, this time on the GPU rather than in a thread pool.

So: two deployments of the same model. An online one, sized for latency, serving queries and nothing else; and a batch one, sized for throughput, which only ever drains the indexing queue. Once they are separate, indexing can run the batch fleet at a hundred percent without a single query noticing.

Why indexing must be a queue, and querying must not

For indexing the argument is not connection fragility — a batch of a few hundred chunks takes about a second, so nothing is at risk of timing out. The argument is what happens when a thousand people upload at once.

Autoscaling cannot outrun a burst. A GPU task takes minutes to become useful: provision the instance, pull the image, load the weights. Scaling is reactive, so it responds to load that has already arrived. With direct calls, the fleet is swamped in the first seconds, calls time out, workers retry, and the retries add load — a cascade during exactly the window in which scaling cannot help. With a queue, the same burst is a number going up. Nothing fails. Capacity arrives three minutes later and starts draining.

A queue is also what makes cheap capacity safe. If a spot instance disappears mid-message the visibility timeout expires and another consumer picks the message up, which is not true of a synchronous call to a machine that has gone away. That is most of the GPU bill.

Scale the consumers on queue depth; alarm on queue age. Depth is the right signal for adding capacity — it says how much work is outstanding. Age of the oldest message is the right thing to promise and to page on, because it is the only number that corresponds to how long a real person has been waiting. "Nothing older than five minutes" is a commitment; "depth under five hundred" means something different every day depending on how large the documents are.

Why generation must not be

Putting the language model behind a queue would be a mistake, for two reasons that are easy to miss.

You cannot stream through a queue. A queue delivers a finished message. Streaming is a byte flow that begins before the answer exists — which is the whole source of the "real time" feeling in Part 4. A queue would give the answer back complete, some seconds later, which is exactly what version 1 already does.

A well-served model wants concurrent connections. Modern inference servers earn their throughput by continuous batching: several in-flight requests are merged into a single pass over the GPU. Feeding such a server one message at a time defeats the mechanism it exists for. Direct concurrent calls are not a compromise there; they are the interface it is designed around.

The credential problem, and its proper answers

A queue only works if the consumer can read it, and this consumer is outside your account. The rule worth holding on to is: never put a long-lived key on a machine you do not control. Everything below is a way of obeying it.

ApproachHow it avoids a stored keyUse when
OIDC federation the platform issues an identity token, swapped for temporary credentials the platform supports it — GitHub Actions, GKE, AKS
IAM Roles Anywhere an X.509 certificate you issued is exchanged for temporary credentials on-prem or another cloud, with somewhere safe for the key
A broker you own the credential never leaves your side; the GPU calls your endpoint instead everywhere else — including Colab
A scoped IAM user it does not — it minimises the damage instead a last resort, with real discipline

For Colab specifically, the first two do not apply. Colab issues no workload identity to federate, and Roles Anywhere would mean keeping a private key in Drive and re-fetching it every session, which is a longer-lived secret than the one it replaces.

So: a broker. The GPU asks a small endpoint of yours for its next job; that endpoint holds the AWS credentials and talks to the queue on its behalf. The GPU holds a token that grants nothing in AWS, that you can revoke by deleting a row, and that only ever lets it receive work.

It has a pleasant side effect. The connection is outbound from the GPU, so the machine needs no public address at all — no tunnel, no ephemeral hostname, and none of the hundred-second limit that shaped so much of version 1.

If you use a scoped IAM user instead, which is defensible while learning, make it deliberate: one queue, exactly ReceiveMessage, DeleteMessage and ChangeMessageVisibility, no wildcards, a dedicated user that does nothing else, rotation on a schedule, and an alarm on unexpected use. What makes that survivable is not the scoping alone — it is that the credential can only take work off a queue. It cannot read your bucket, touch your database, or start an instance.

On a GPU host inside your own network this entire section evaporates: the container gets a task role like everything else. The difficulty is not queues, it is somebody else's computer.

What we actually build, and what we do not

One GPU. No autoscaling. On purpose.

Everything above about scaling the GPU side is design, not deliverable. In this course the three model services run on a single Colab runtime. There is no fleet to scale, no spot capacity, and no second deployment — one card, and whatever it can do.

That is a budget constraint rather than a design opinion, and it is written down here so that nobody mistakes the gap for an oversight. Concretely, what changes:

Design saysWe run
batch fleet, autoscaled on queue depthone process, fixed size
separate online and batch embedding deploymentsone deployment doing both
spot capacity, scaled to zero when idlea Colab runtime that is either on or off
indexing latency held under an SLOwhatever one GPU manages — expect a backlog

The queue still earns its place, even with one consumer. This is the important part. A queue in front of a single GPU is not a scaling mechanism there — it is a way of making one slow consumer safe. A thousand uploads arriving at once become a backlog rather than a thousand failed connections; a Colab runtime dying halfway through loses nothing, because unacknowledged messages come back; and the depth of that queue is a number that tells you honestly how far behind you are. None of that requires a second instance.

What we optimise instead is the one card: batching, quantisation, kernel and runtime choices, keeping models warm. That is a different discipline from everything else in this document, and it is where the remaining headroom is when you cannot buy more hardware.

And this is the point of building the rest properly. Every AWS decision here is made as though the GPU side will one day scale, so that when there is budget, it is a configuration change and not a redesign: raise a desired-count, point the queue at a real fleet, split the embedding deployments. The application does not learn about any of it. The single GPU is a known ceiling with a door in it — which is a different thing from an architecture that cannot grow.

Part 7What version 2 does not solve

A design document that only lists victories is not much use. These are open, and knowing them is part of the design.

A

The GPU is still the ceiling — and in this course it is one card

Every improvement here moves work to the model services faster. If they saturate, a deeper queue is all you have bought, and the honest fix is more GPU, a smaller model, or better batching.

For this project that ceiling is concrete: a single Colab runtime, no fleet, no autoscaling. Expect an indexing backlog under load. The queue makes that a wait rather than a failure, which is the most an architecture can do about a hardware limit.

Alarm on queue age. Shed load rather than accept work you cannot do. Then optimise the one card — batching, quantisation, warm models.
B

Cost scales with success

Fargate, RDS, ElastiCache, NAT gateways and a load balancer have a floor of a few hundred dollars a month before a single user arrives — perhaps twenty times what version 1 costs.

Justify it with users, not with architecture. Version 1 is the right answer for a class.
C

More moving parts, more ways to be subtly wrong

At-least-once delivery means duplicate work if a handler is not idempotent. A queue can silently fall behind. Two systems can disagree in ways one system never could.

Idempotent handlers, alarms on queue age, and traces — which is why observability is not optional here.
D

Retrieval quality is untouched

None of this makes an answer better. Chunking strategy, re-ranking, and prompt assembly decide that, and they are identical in both versions.

A separate problem, and the one with the most headroom left in it.
E

One region

Everything here lives in one AWS region. A regional outage is an outage.

Multi-region is a different design and a much larger bill. Name it, do not build it yet.

Part 8The order of work

This is not a rewrite. Each step below is shippable on its own, and each one leaves a working system — which matters, because a migration that only pays off at the end usually does not get finished.

  1. Postgres and Redis. Both are settings changes: DATABASE_URL and MEMORY_BACKEND already exist and already select an implementation. No new architecture, and it removes the two limits that kill data.
  2. The queue and the workers. The big one. Replace background.add_task with an SQS write, and move ingest.run and chat.answer into worker processes almost unchanged — they are already self-contained functions that open their own database session, which is exactly the shape a worker needs.
  3. Containers, load balancer, autoscaling. Now that the API is stateless and does no slow work, running many of it is safe.
  4. pgvector. Move the index into the database. Re-index everything, since vectors from two models are not comparable.
  5. The transcription queue. Turn the last synchronous call into a message the GPU pulls, with presigned URLs in both directions and a broker holding the credentials. This is what finally makes a long video safe.
  6. Streaming. SSE plus Redis pub/sub. The first change users will actually feel.
  7. Identity, quotas, WAF. Necessary before anyone outside the room uses it.
  8. Observability. Last in the list, first thing you will want at three in the morning. Do not leave it out.
Notice what does not change

The pipeline functions, the chunker, the prompt assembly, the storage abstraction, the service contracts, and the entire frontend other than swapping a poll for an event source. Version 1 put the slow work in the wrong place; it did not write it wrongly. Most of the code survives the move, and that is a good sign about how version 1 was structured.

Version 1 is the version you can hold in your head, and it is the right thing to have built first: every limitation in it is one you can now name, reproduce, and explain. Version 2 is what those limitations cost to fix.

Build it when you have users. Not before.

And when you do, notice which half of this document you will actually need to act on. The AWS side is written so that growing it is a configuration change. The GPU side is one card with a door in it, and walking through that door costs money rather than a redesign. Those are the two kinds of constraint worth being able to tell apart.
